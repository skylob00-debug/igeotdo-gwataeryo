 이것도 과태료? — 프로젝트 기록 및 계획
 최종 갱신: 2026-09-19

이 문서는 지금까지의 분석 근거, 확정된 결정, 현재 상태, 앞으로 할 일을 담는다.
"왜 이렇게 했는지"를 남기는 것이 목적이다. 근거가 없으면 다음 사람이 같은 벽에
다시 부딪히고, 최악의 경우 이미 탈락시킨 방법으로 되돌아간다.

파이프라인 기술 상세는 pipeline/README.md 에 있다.
Claude 세션용 작업 규약은 CLAUDE.md 에 있다.


================================================================================
 1. 제품 정의
================================================================================

운전자 대부분은 자기가 과태료 대상이 되는 행위를 "몰라서" 위반한다.
금액의 법적 원천인 도로교통법 시행령 별표는 법제처에 HWP/PDF로만 존재해
일반인이 읽기 어렵고, 법이 개정돼도 알 방법이 없다. 이 앱은 그 간극을 메운다.

앱 이름: 「이것도 과태료?」 (2026-09-19 확정)
  앱의 핵심 경험이 "어, 이것도 과태료야?" 하는 순간이라 제목에 그대로 담았다.
  물 튀김 과태료, 2시간 넘기면 오르는 주정차, 보호구역 2배 같은 것들.
  스토어 표시명에만 물음표를 쓰고 패키지 식별자는 따로 간다.

[ 하는 것 ]
  - 몰랐다가 과태료 무는 경우를 카드로 알려준다
  - 근거 조문 / 금액 / 시행일을 항상 함께 보여준다
  - 도로교통법이 개정되면 푸시로 알린다

[ 안 하는 것 — 기술적으로 불가능하다 ]
  - 개인 미납 과태료 조회
      이파인(efine.go.kr)은 로그인 기반이고 공개 API가 없다.
      앱에서는 이파인 딥링크로 보내는 것까지만 한다.
  - 실시간 단속 알림
      단속 데이터는 개인정보라 공개되지 않는다.

이 구분은 기획이 흔들릴 때 돌아올 지점이다. 위 두 가지를 만들려는 시도가
나오면 이 문단을 먼저 읽을 것.

--------------------------------------------------------------------------------
 2.1 데이터 전략: 사전 구축 DB + 개정 감지  (실시간 API 조회는 불가능)
--------------------------------------------------------------------------------

법제처 별표 목록 API를 실제로 호출한 결과:

  GET law.go.kr/DRF/lawSearch.do
      ?OC=test&target=licbyl&search=2&query=도로교통법 시행령&type=XML

  <licbyl>
    <별표번호>000600</별표번호>
    <별표명>과태료의 부과기준(제88조제4항 본문 관련)</별표명>
    <별표서식파일링크>/LSW/flDownload.do?flSeq=164726371</별표서식파일링크>      (HWP)
    <별표서식PDF파일링크>/LSW/flDownload.do?flSeq=164726373</별표서식PDF파일링크>  (PDF)
  </licbyl>

=> 제목과 파일 다운로드 링크만 온다. 표 내용은 구조화 텍스트로 제공되지 않는다.
=> 따라서 "앱이 실시간으로 API를 조회해 금액을 보여준다"는 구조는 성립하지 않는다.
=> 원본을 한 번 뜯어 DB로 만들고, 이후 개정을 감지하는 방식이 유일한 길이다.

--------------------------------------------------------------------------------
 2.2 원본 형식: HWP 채택  (PDF 아님)
--------------------------------------------------------------------------------

세 가지 원천을 모두 시험했다.

  원천                          띄어쓰기        셀 병합 구조       결과
  ---------------------------- --------------- ----------------- --------
  별표 HTML (lsBylInfoP.do)     —               —                 탈락
  별표 PDF (pdfplumber)         X 줄바꿈 소실   X 좌표로 추정      탈락
  별표 HWP                      O 문단 원문     O rowSpan/colSpan  채택

  - HTML: JS 렌더링이라 서버에서 읽히지 않는다. iframe 껍데기만 온다.
  - PDF : 텍스트 추출은 되지만 줄바꿈 지점에서 한글 띄어쓰기가 사라진다.
          "어린이통학버스 운전자의 의무 위반" -> "운전자의의무"
          이건 복구 불가능하다. 여백 크기로 판별을 시도했으나 판별력이 없었다.
          표 구조도 좌표로 추정해야 하고, 금액 셀이 세로 병합돼 있어
          어느 위반행위가 어느 금액을 쓰는지 정확히 알 수 없다.
  - HWP : 레이아웃 줄바꿈이 없는 실제 문단 텍스트를 갖고 있고,
          표 셀마다 col/row/colSpan/rowSpan이 들어 있다.
          의존성은 olefile 하나로 끝난다.

법령 API의 <별표내용>이 주는 박스아트 표(┏━┯━┓)는 추출에 쓰지 않는다.
셀 병합 정보가 없기 때문이다. 다만 원문이 바뀌었는지 판단하는 해시 기준으로는
받아 둔다. 검수 과정에서 렌더링 위치를 보는 보조 근거로도 썼다.

*** PDF 파싱으로 돌아가지 말 것. 위 표가 그 이유다. ***

--------------------------------------------------------------------------------
  [실제 버그 1건]
    별표 8 제38호가 '삭제' 항목이라 근거 법조문이 하나 적었고, 그 탓에

  [파서 한계 6건 해소]
    열거 기호(1)) 없이 문단만 나열된 금액과 '차종 구분 없음:' 같은 라벨 줄을

      별표 8 제67호   가목 15만원 / 나목 10만원

  [남은 9건은 overrides.json 에 근거와 함께 확정]
    자동으로 못 푸는 경우는 8건 + 1건이었다.

    (1) 목이 4개인데 금액 묶음이 2개 — 별표 6 제4의2호, 제6의4호 (8건)

          근거 2: 법제처 박스아트 렌더링에서 금액 묶음이 찍힌 줄 위치

        제4의2호  가(제18조 횡단·유턴·후진)     범칙금 7/6/4 -> 과태료 8/7/5만

 5.2 별표 7·10 추가 (보호구역)   [완료 2026-09-19]
--------------------------------------------------------------------------------
    별표 7  어린이보호구역 및 노인·장애인보호구역에서의 과태료 부과기준  7건
    별표 10 어린이보호구역 및 노인·장애인보호구역에서의 범칙행위 및 범칙금액  16건

  둘 다 검수 0건으로 자동 추출됐다. 걱정했던 시간대(08~20시) 조건은 별표
  본문이 아니라 도로교통법 제12조에 있어 표에는 나타나지 않았다.
  대신 같은 항목이 "어린이보호구역"과 "노인·장애인보호구역"으로 갈린다.

  보호구역 vs 일반 도로 (승용차 기준):
    신호·지시 위반      과태료  7만 -> 13만    범칙금  6만 -> 12만
    속도위반 60㎞/h 초과  과태료 13만 -> 16만    범칙금 12만 -> 15만
    주정차 위반         어린이 12만 / 노인·장애인 8만

  파서에서 고친 것 두 가지 (별표 6·8 에도 영향):
    1. 항목과 첫 목이 한 셀에 있고 나머지 목이 다음 행들에 오는 구조
       (별표 7 제2호). 고치기 전에는 나·다·라목이 통째로 버려졌다.
    2. 한 항목의 금액 열거가 두 행에 걸쳐 잘린 구조 (별표 6 제2의3호).
       앞 행에 "1) 승합 4만, 2) 승용 4만", 뒤 행에 목 다섯 개와 "3) 이륜 3만".
       열거가 1) 로 다시 시작하지 않으면 이어짐으로 본다.

  2번은 기존 데이터의 실제 누락이었다. 별표 6 제2의3호가 1건으로 뭉쳐 있었고
  이륜자동차 금액 3만원이 통째로 빠져 있었다. 목 5건으로 분리되면서
  적재 시 옛 행(byeolpyo6-2-3)이 자동으로 삭제됐다.
  건수 스냅샷 테스트가 68 -> 72 변화를 잡아내 발견했다.

 5.7 FCM 푸시   [실기기 발송 확인 2026-09-19]
--------------------------------------------------------------------------------
  패키지 식별자: kr.co.igeotdo.gwataeryo  (android + ios 양쪽 확정)

  구조
    app/lib/core/push.dart              토큰 발급·등록·토픽 구독, 수신 스트림
    app/lib/core/env.dart               FIREBASE_* 네 값을 빌드 인자로 받는다
    app/lib/main.dart                   배경 핸들러, 배지, 알림 탭 이동
    supabase/functions/push-notify/     보내는 쪽 (Deno Edge Function)

  보내는 규칙
    published=true 이고 push=true 이고 notified_at is null 인 것만 나간다.

    published 와 push 를 가른다 (0006_push_flag.sql).
      published  앱 알림 목록에 나오는가   (사람이 검수해 켠다)
      push       그중 푸시까지 보내는가    (기본 켬)
    앱에 들어와 훑어볼 값은 있지만 자는 사람 폰을 울릴 값은 아닌 건이 있다.
    시행규칙 별표 28(벌점) 개정이 그랬다. 하나로 묶여 있으면 둘 중 하나를
    포기해야 한다. 기본을 true 로 둔 이유는 켜는 것을 잊어 아무에게도 안 가는
    사고가 끄는 것을 잊는 쪽보다 크기 때문이다.

    검증 (2026-09-19, 0006 적용 후)
      기존 4건에 기본값 push=true 가 들어갔다.
      임시 행 둘(published=true, push 는 각각 true/false)을 넣고 dry-run 하니
      push=true 인 것만 집혔다. 임시 행은 지웠다 — id 5, 6 은 소모됐으므로
      다음 실제 행은 7 부터다 (bigserial 이라 되돌리지 않는다).

    보낸 뒤에만 notified_at 을 찍는다. 실패하면 다음 실행에서 다시 집힌다.
    토픽 하나(law-changes)로 쏜다. 기기 토큰을 하나씩 도는 방식은 지금
    규모에 이르지 않았고 만료 토큰 청소라는 일거리만 늘린다.
    devices 테이블은 등록은 받아 두되 발송에는 아직 쓰지 않는다.

  google-services.json 을 쓰지 않는다
    그 파일을 넣으면 google-services Gradle 플러그인이 딸려 오고, 파일이 없는
    빌드가 통째로 깨진다. FirebaseOptions 네 값을 --dart-define 으로 넘긴다.
    값이 없으면 푸시만 건너뛰고 앱은 그대로 돈다 (Push.start 가 조용히 빠진다).

  Android 알림 채널
    AndroidManifest 의 default_notification_channel_id = law_changes.
    push-notify 가 보내는 android.notification.channel_id 와 같아야 한다.
    Android 8+ 는 채널이 없으면 알림이 아예 뜨지 않는다. 이름만 적어 두면
    FCM SDK 가 만들어 준다.

  사람이 해야 할 일 (Firebase 콘솔)
    1. console.firebase.google.com > 프로젝트 추가
       Google Analytics 는 꺼도 된다 (푸시에 필요 없다).
    2. Android 앱 추가 > 패키지 이름 kr.co.igeotdo.gwataeryo
       google-services.json 을 받되 프로젝트에 넣지 말고 따로 둔다.
    3. 값 네 개를 뽑아 .env 에 넣는다
         .venv/Scripts/python.exe pipeline/firebase_env.py <받은 파일 경로>
       콘솔에서 눈으로 옮겨도 되지만 Android 앱의 API 키는 '웹 API 키'와
       다를 수 있다. 파일에서 뽑는 쪽이 확실하다.
    4. 프로젝트 설정 > 서비스 계정 > 새 비공개 키 생성 -> JSON 파일
       로컬: .env 의 FIREBASE_SERVICE_ACCOUNT_FILE 에 경로
       운영: Supabase > Edge Functions > Secrets 에
             FIREBASE_SERVICE_ACCOUNT = JSON 내용 전체
       이 키는 발송 권한이다. 앱에 절대 넣지 않는다.
    5. push-notify 함수 배포 (law-watch 와 같은 방식)
       Verify JWT 는 끈다. 함수가 CRON_SECRET 을 직접 확인한다.
    6. iOS 는 나중에. APNs 인증 키(.p8)를 Firebase 에 올려야 하고
       GoogleService-Info.plist 대신 같은 네 값을 쓰면 된다.

  확인 순서
    .venv/Scripts/python.exe pipeline/export_seed.py        # env.json 갱신
    cd app && flutter run --dart-define-from-file=env.json  # 토큰 등록 확인
    node --experimental-strip-types supabase/functions/push-notify/local.ts
                                                            # 무엇이 나갈지만
    ... --send --id <번호>                                   # 한 건만 실제 발송

  겪은 문제 둘
    1. flutter install 이 예전에 만든 통합 APK(app-release.apk)를 올렸다.
       Firebase 값을 넣기 전 빌드라 '설정이 없어 푸시를 건너뜁니다' 가 떴다.
       split-per-abi 로 뽑은 arm64 판을 adb install 해야 맞다.
       두 빌드는 versionCode 도 다르다(통합 1 / arm64 2001). 섞으면

       AndroidManifest 의 default_notification_channel_id 는 '이 채널을 써라'
       고 지정할 뿐 채널을 만들어 주지 않는다. firebase_messaging 플러그인도
       만들지 않는다. MainActivity.onCreate 에서 직접 만든다.
       만들지 않으면 사용자가 알림 설정에서 '기타' 라는 이름을 보게 되고,
       끄고 켜는 기준도 우리 것이 아니게 된다.

    cd app && dart run flutter_native_splash:create

  적용하며 걸린 것 셋

    1. 적응형 전경이 두 번 줄어든다
       flutter_launcher_icons 는 전경에 16% 안쪽 여백을 기본으로 넣는다.
       원본을 이미 안전영역에 맞춰 뽑는데 여기서 또 줄이면 마크가 네모
       아이콘보다 눈에 띄게 작아진다. adaptive_icon_foreground_inset: 0.
       원본은 icon.png 와 같은 구도(마크가 캔버스의 50%, 108dp 중 54dp)로
       두어 72dp 안전영역 안에 들어가면서 네모와 크기가 맞는다.

    2. Android 12 스플래시는 규격이 따로 있다
       1152x1152 캔버스에 가운데 지름 768 원만 보인다. 바깥은 잘린다.
       512 짜리를 주면 도구가 늘여서 잘려 나간다. 마크가 그 원의 6할쯤을
       먹게 잡는다 — 캔버스에 맞춰 작게 그리면 혼자 쪼그라들어 보인다.
       icon_background_color 는 주지 않는다. 주면 보이는 영역이 768 에서
       512 로 줄고, 종이색 위에 종이색 원을 얹는 셈이라 값도 없다.

    3. 다크 모드에서 검정이 한 번 번쩍인다
       스플래시(LaunchTheme)와 첫 프레임 사이에 NormalTheme 이 잠깐 보인다.
       기본값 ?android:colorBackground 는 다크 모드에서 검정이다.
       라이트 전용인 이 앱에서는 종이색 -> 검정 -> 종이색이 된다.
       values*/styles.xml 네 개의 NormalTheme 을 @color/app_background 로
       고쳤다. colors.xml 의 app_background = #FFFDF9 = AppColors.paper.
       (native_splash 를 다시 돌려도 NormalTheme 은 건드리지 않는다. 확인함)

  Android 12+ 는 스플래시를 시스템이 그린다. 개발자가 주는 것은 아이콘과
  배경색뿐이다. 앱 이름을 그림에 넣지 않는다 — 원에서 잘려 나간다.
  앱이 번들 seed 로 바로 뜨므로 스플래시에 최소 노출 시간을 걸지 않는다.

  검증: 적응형 원형 마스크 / 72px / 48px, Android 12 보이는 영역,
        구형·iOS splash.png 를 모두 눈으로 확인. APK 빌드 통과.

  무엇은 원문으로 확인해야 하는지 처음에 갈라 두면 뒤의 모든 화면이 쉬워진다.

  네 가지
    1. 법령 원문을 정리해 보여준다 (앱이 금액을 계산하거나 어림하지 않는다)
    2. 법적 효력은 없다 (사안·기관·경감/가중에 따라 달라진다)
    3. 이 정보를 믿고 한 판단에 책임지지 않는다
    4. 언제든 원문으로 갈 수 있다 (근거 조문·시행일·원문 링크를 늘 함께 둔다)

  저장: SharedPreferences 의 disclaimer_version 에 판 번호.
        Repository.consentVersion 을 올리면 다시 한 번 뜬다.
        문구가 실질적으로 바뀌었을 때 올린다.

  면책을 읽기도 전에 알림 권한을 묻는 것은 무례하고 거절률도 높다.

    위젯을 그리지 않는 검사는 test 로 쓴다.

  나머지 brand/*.png 는 빌드 도구 전용이라 번들에 넣지 않는다.
